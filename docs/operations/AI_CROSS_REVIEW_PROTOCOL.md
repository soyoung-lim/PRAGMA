# PRAGMA AI 협업·독립 검토 프로토콜

## 적용 상태

- 2026-08-10 사용자 확정
- 사용자가 변경 또는 종료를 명시할 때까지 기본 작업 방식으로 적용한다.
- 개별 작업에서 사용자가 다른 역할 배분을 지정하면 그 지시가 우선한다.

## 기본 역할

- **Codex = 메인 실행 책임자**
  - 저장소 조사, 구현, 테스트, 브라우저 E2E, Git 상태 확인, 배포 준비, 연구·개발 기록을 한 흐름으로 담당한다.
  - 작업마다 독립 검토 필요성을 판단해 아래 flag 중 하나를 명시한다.
- **Claude Code = 선택적 독립 검토자**
  - Codex 작업 전체를 처음부터 반복하지 않는다.
  - 전달받은 commit·diff·테스트 결과·데이터·쟁점에 한정해 반대 가설, 누락, 분모 오류,
    연구 주장 과장과 구조적 위험을 읽기 전용으로 검토한다.
  - 사용자의 별도 지시가 없으면 앱 코드·DB·프롬프트·배포 상태를 변경하지 않는다.

두 모델은 같은 기능과 같은 worktree를 동시에 편집하지 않는다. 독립 검토는 중복 구현이 아니라
검증된 산출물에 대한 범위 제한 독립 검토다.

## Codex 독립 검토 flag

### `[독립 검토 필수]`

- DB migration, RLS, Auth 또는 핵심 schema 변경
- 기존 데이터의 소급 갱신·삭제·대량 수정
- 대량 콘텐츠 생성, 콘텐츠 LOCK 또는 release 확정
- production 배포 중 되돌리기 어렵거나 연구 자료에 영향을 주는 변경
- 연구 통계의 분모·분자 확정, 핵심 논문 주장 또는 결과 해석

Codex는 실행 또는 최종 확정 전에 검토 이유, 정확한 대상, 확인 질문과 증거 묶음을 제시한다.

### `[독립 검토 권고]`

- 중요한 학습·평가 설계 변경
- 생성·검수 기준, 외부 모델 검토 범위와 중대한 아키텍처 선택
- KCI 논문의 논지·구성·투고 전략
- 한 모델의 판단만으로 확정하기에는 대안 비용이나 연구적 영향이 큰 경우

사용자가 시간과 중요도를 보고 Claude 검토 여부를 선택할 수 있다.

### `[단독 진행 적합]`

- 범위가 작은 UI·문구 수정
- 원인이 확인된 국소 버그 수정과 회귀 테스트
- 타입·lint·테스트 보강, 동작 변화 없는 정리
- 읽기 전용 조사로 사실이 충분히 확인되고 되돌리기 어려운 영향이 없는 작업

Codex가 구현·검증하고 별도 중복 검토를 요청하지 않는다.

## 표준 운영 순서

1. Codex가 현재 worktree·branch·HEAD와 정본을 확인한다.
2. Codex가 구현 또는 분석을 완료하고 실제 검증 결과를 남긴다.
3. 독립 검토가 필요하면 작업을 멈추고 flag, 검토 범위와 증거 묶음을 제시한다.
4. Claude는 아래 프롬프트로 읽기 전용 독립 검토를 수행한다.
5. Codex가 Claude 지적을 코드·데이터·정본과 재대조해 `수용 / 부분 수용 / 기각`으로 통합한다.
6. 정책·연구 해석이 계속 충돌할 때만 사용자가 최종 결정한다.

## Claude Code 전달용 표준 프롬프트

아래 블록의 대괄호 부분만 작업에 맞게 채운다. 독립 판단이 특히 중요하면 Codex의 최종 결론은
먼저 주지 않고 증거와 질문만 전달한다.

```text
당신은 PRAGMA 프로젝트의 메인 구현자가 아니라 독립 검토자입니다.

현재 기본 역할은 다음과 같습니다.
- Codex: 메인 실행 책임자 — 조사, 구현, 테스트, 브라우저 E2E, Git·배포 준비, 기록 담당
- Claude Code: 선택적 독립 검토자 — Codex 산출물의 누락, 반대 가설, 회귀 위험,
  분모 오류, provenance 문제와 연구 주장 과장을 검토
- 이 역할 분담은 사용자가 변경한다고 명시할 때까지 유지합니다.

이번 검토는 읽기 전용입니다. 사용자가 별도로 요청하지 않는 한 코드·DB·프롬프트·문서·Git·배포
상태를 수정하지 마세요. 관련 구조 전체를 다시 설계하거나 같은 구현을 반복하지 말고, 아래 대상과
질문에만 답하세요.

[검토 대상]
- worktree / branch / commit: [정확한 값]
- 변경 또는 분석 요약: [요약]
- 관련 diff·파일: [경로 또는 commit]
- 실행된 검증: [테스트·E2E·쿼리 결과]

[검토 질문]
1. [질문 1]
2. [질문 2]
3. [필요 시 질문 3]

[검토 규칙]
1. 직접 확인한 사실, 문서·코드에서 한 추론, 아직 확인하지 못한 가정을 구분하세요.
2. 비율이나 보급률을 제시하면 분자·분모·대상 기간·적격 조건을 명시하세요.
3. 기술적으로 가능하다는 사실만으로 계약상·연구방법론상 허용된다고 결론 내리지 마세요.
4. 현재 worktree와 commit을 확인하고 다른 worktree나 과거 기록을 현행 상태로 오인하지 마세요.
5. 기존 Codex 결론에 동의하는 것보다 반증 가능한 허점과 누락을 우선 찾으세요.
6. 검토 범위를 벗어난 개선안은 별도 항목으로 분리하고, 지금 필요한지 여부를 표시하세요.

[출력 형식]
- 종합 판정: 수용 / 부분 수용 / 기각
- 발견 사항: P0 / P1 / P2 순서, 각 항목에 근거 경로 포함
- Codex 결론별 판정: 수용 / 부분 수용 / 기각 및 이유
- 추가로 필요한 검증
- 연구 주장으로 사용할 수 있는 범위와 사용할 수 없는 범위
- 코드나 데이터를 직접 변경하지 않았다는 확인
```

## 예외

- KCI 제목·논지·초록처럼 독립적인 발산 자체가 목적인 작업은 두 모델이 각각 독립안을 낼 수 있다.
- 긴급한 빌드 중단급 국소 수정 등은 사용자가 한 모델에 바로 맡길 수 있다.
- 어느 경우에도 역할 분담이 push·merge·PR·배포·DB 변경의 기존 승인 게이트를 대체하지 않는다.
