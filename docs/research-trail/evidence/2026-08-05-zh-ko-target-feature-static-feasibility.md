## 2. 판정 규칙

- `통과`: 기준 1~4가 모두 충족되고, 기준 5에서 R5 hard fail이 예상되지 않는다.
- `보류`: 동일 명제 또는 gate1 경계가 AI 단독 판정으로 확정하기 어렵다.
- `실패`: 축의 한쪽 대역을 만들기 위해 사실 삭제·추가 또는 화행 변질이 사실상 필요하다.
- R5의 `과소안 최단`·`과잉안 유일 최장` warning은 기록하되 단독 실패로 쓰지 않는다.
- 글자 수는 JavaScript code point 기준이며 공백·문장부호를 포함한다. 실제 미션은 5후보이므로
  이 3안 점검은 R5 최종 통과를 보증하지 않는다.
- 명제 위반과 강도 자원의 경계는 2축 판정 종합 §2·§3을 따른다. 외부 사건·검증 가능한
  사실·구체적 약속은 새 명제지만, 관습적 강조·화자의 심리 표출은 강도 자원으로 허용한다.
  단, ‘강도·양만으로 과잉 도달’은 감사 축에서 확인된 잠정 가설이지 전 축 자동 안전 규칙이
  아니다.
- 반복 3연발은 `answer_cue`가 되므로 금지하고 강조는 2겹까지 사용한다.

## 6. Fable 교차검증 반영 판정

- 수용: 요청·제안·반대의 원안 통과, 정적 점검은 E1 측정이 아니라 필요조건이라는 해석,
  글자 수 30건 일치와 R5 hard fail 0 검산.
- 보완 수용: 거절·감사·초대 문장 수정, 사과·칭찬 대응의 통과 상향, 불만의 구조적 실패 기각.
- 추가 보완: 사과는 `전적으로 모든 책임` 대신 관습적 책임 감정만 확대했다. 불만 과소안은
  사실 추상화에 기대지 않고 원명제를 유지한 채 책임 처리만 부족하게 했다. 칭찬하기 3중
  최상급도 확정 규칙 ⑦에 맞춰 두 겹으로 줄였다.
- 기각: 재개 기록과 `model_returned` 확인이 필요하다는 절차 노트. 실행 증거 문서에 1차
  22셀과 2차 8셀을 분리했고, 최종 원장 표에 요청·반환 모델·fallback 0을 이미 기록했다.
- 보류 유지: gate1·C2 프롬프트의 문구 개정. 이는 계약 인접 변경이므로 실제 소수 조립에서
  정의 상호작용이 관찰된 뒤 별도 승인으로 다룬다.
