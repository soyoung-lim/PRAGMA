# PRAGMA 화용 학습·연구 설계 원칙

- 상태: **사용자 합의 완료 — 연구·개발 공통 기준**
- 확정일: 2026-07-27
- 적용 범위: 시나리오 코어, MPJ 5문항, DCT 번역·통역, AI 피드백, 품질 감사, 연구 분석
- 성격: 개념·구인 정본. 개별 코드·DB 변경은 이 문서를 바탕으로 별도 검토한다.

## 한 문장 원칙

> PRAGMA는 직접성이나 특정 표현 자체를 평가하지 않고, 하나의 중심 상호작용 목적이 관계·권리·부담·매체에 맞게 어떤 발화 구성으로 실현되었는지를 판단한다.

## 기본 분석 구조

PRAGMA는 다음 네 층을 분리한다.

```text
① 교육 과제 유형
→ ② 상호작용 순서
→ ③ 실제 발화 구성
→ ④ 상황에 따른 적절성 평가
```

예를 들어 거절은 다음과 같이 본다.

```text
교육 유형: 거절
상호작용: 요청·제안·초대에 대한 반응
발화 구성: 거절 본체 + 사과·이유·대안 등
평가: 관계·부담·상황에 이 구성이 적절한가
```

## 생성 조건의 위계

PRAGMA의 생성 필드는 모두 필요하지만 동등한 연구축은 아니다.

```text
연구 구인 행렬: 화행 × P × D × R
과업 트랙: task_mode (번역 | 통역)
교육 편성층: learner_level + domain
사건·검색 메타: theme + topic (+ work의 industry)
내부 호환성 해결층: context_spec
```

- 논문에서 `243개 조합`이라 할 때는 `화행9 × P3 × D3 × R3`을 뜻한다.
- `화행9 × 수준3 × mode2 = 54셀`은 콘텐츠 전달·운영 커버리지다. 구인 행렬 243셀과 같은 표가 아니다.
- 500건은 모든 축의 완전요인 교차가 아니라, 243 구인셀을 채우면서 수준·도메인·mode의 주변분포를 확보하는 층화 표집이다.
- `domain`(일상·학업·직장), `theme`, `topic`, `industry`를 화용적 적절성의 독립 원인으로 과장하지 않는다.

## 1. 단일 화행 원칙

`Head Act는 정확히 하나여야 한다`는 규칙은 사용하지 않는다. House & Kádár는 동일한 화행을 실현하는 multiple heads, Head Act 앞뒤의 Supportive Moves, Supportive Move의 Head Act 승격, 여러 문장으로 이루어진 extended speech-act set을 모두 인정한다.

PRAGMA의 기준은 다음과 같다.

> 하나의 focal interactional target을 유지한다.

- 같은 목적을 실현하는 multiple heads: 허용
- Head Act 전후에서 중심 행위를 완화·강화하는 Supportive Moves: 허용
- 이유·사과·대안 등이 포함된 자연스러운 화행 묶음: 허용 가능
- 별개의 상호작용 목적이 동등한 비중으로 경쟁: 과업 초점 오염

따라서 `단일 화행 시드`는 실제 발화에 화행이 하나만 존재해야 한다는 뜻이 아니다. 교육적으로 평가할 중심 상호작용 행위가 하나라는 뜻이다.

## 2. 거절의 지위

`refusal`은 화행이자 교육 과제 유형으로 유지한다. 중간언어 화용론과 교수학습 연구에서 충분히 확립된 분류다.

동시에 House & Kádár의 상호작용적 관점을 분석 보조층으로 사용한다.

```text
pedagogical_task_type: refusal
interactional_position: response
eliciting_act: request | suggest | invite
realisation_strategy: 직접 거절 | 유보 | 이유 | 대안 등
```

House & Kádár의 분류는 거절 연구를 부정하는 유일한 정답이 아니라, 거절을 더 작은 화행과 상호작용 순서로 재분석하는 하나의 이론적 렌즈다.

## 3. 명제 보존과 Supportive Move

다음 두 종류를 구분한다.

### 비명제적·관습화 자원

- 사과·인사 공식
- 완화어
- 호칭과 Alerter
- Downgrader 등

### 명제적 Supportive Move

- 구체적 이유
- 대안
- 약속
- 보상 등

MPJ 번역 후보에서 원문에 없는 이유·대안·약속을 추가하면 화용 차이뿐 아니라 의미 차이가 발생한다.

> 명제적 Supportive Move는 원문이 허용할 때만 후보에 포함한다. 후보 간 차이는 원칙적으로 동일한 명제 내용을 어떻게 화용적으로 실현하는가에 둔다.

자유 산출 DCT에서는 학습자가 Supportive Move를 선택할 수 있다. 이때 번역 충실성과 화용적 조정을 분리해 평가한다.

## 4. Standard Situation과 권리·의무

Standard Situation은 P·D·R을 대체하는 새 조합축이 아니다. 기존 셀 좌표와 주제를 구체적인 역할·권리·의무로 실현하는 내부 제약이다.

```text
화행 + P·D·R + task_mode + domain
→ 호환 가능한 topic 선택
→ 서버가 상황 템플릿 선택
→ 역할·권리·의무·결정 권한 확정
→ 자연스러운 상황 서술 생성
```

최소 내부 정보는 다음으로 제한한다.

```text
standard_situation_code
role_pair
speaker_entitlement
addressee_obligation
decision_authority
```

- 독립 조합축으로 사용하지 않는다.
- 학습자 화면에 항목식으로 노출하지 않는다.
- 생성 프롬프트와 품질 감사의 일관성 조건으로 사용한다.
- 하나의 `context_spec` 객체로 관리하고 모델 응답이 아니라 서버가 주입한다.

핵심은 역할명을 늘리는 것이 아니라 `누가 무엇을 요구하거나 결정할 권한이 있는가`를 구체적으로 고정하는 것이다.

topic은 상황을 결정하는 다섯 번째 화용축이 아니다. `무슨 사건이 있었는가`를 제공하는 소재다. 따라서 topic 시드는 원칙적으로 P·D 관계와 전달 매체를 고정하지 않는다. 추천서·길 묻기처럼 사건의 성립 자체가 특정 관계를 요구하는 예외만 허용 P·D를 선언하고, 호환되지 않는 셀에서는 선택하지 않는다.

직장 `industry`도 연구축이 아니라 편성·검색용 배경 메타데이터다. 다만 행 태그와 실제 내용이 어긋나지 않도록 직장 셀에서는 생성 프롬프트에 전달하고, 비평기가 실제 업무·대상·어휘의 산업 정합성을 별도 감사한다. 산업은 화행·P·D·R·topic을 덮어쓸 수 없다.

## 5. 수행 방식과 매체

매체를 공손성이나 격식의 자동 결정축으로 사용하지 않는다. `이메일이므로 공손하다`와 같은 추론은 금지한다.

`task_mode`는 반드시 보존하되 P·D·R과 별개의 과업 트랙으로 다룬다.

```text
task_mode: translation | interpreting
```

- 번역과 통역은 별도 MPJ5+DCT1 흐름과 분석층으로 분리한다.
- `channel`이나 `medium`을 다시 독립 배치축으로 부활시키지 않는다.
- 실제 장면에 필요한 동시성·기록성 등은 `context_spec`이 상황을 실현할 때 정하며, 관찰 메타데이터로 저장할 수는 있다.
- topic 이름이나 시드가 `DM`, `단체방`, `이메일`을 미리 박아 mode를 몰래 결정하지 않게 한다.
- 서로 다른 수행 방식의 결과를 같은 조건처럼 단순 합산하지 않는다.

## 6. 직접성과 공손성

다음 개념을 엄밀하게 분리한다.

```text
직접성 = 발화 의도가 표현에 얼마나 명시적으로 나타나는가
공손성 = 관계를 어떻게 관리하는가
부담 = 상대에게 요구되는 비용·위험
격식 = 상황·장르에 맞는 표현 양식
적절성 = 이 선택들이 현재 상황에 맞는가
```

- 직접적이어도 적절하고 공손할 수 있다.
- 간접적이어도 어색하거나 책임 회피처럼 들릴 수 있다.
- 완화 표현이 많다고 반드시 공손하지 않다.
- 격식적이라고 반드시 화용적으로 적절하지 않다.

시스템의 개념층도 다음처럼 분리한다.

```text
directness_code       // 기술적 분류
politeness_feature    // 공손성이 실제 학습 초점일 때만
appropriateness_band  // 상황 대비 평가
```

`directness_code`는 자동으로 정답·오답이나 가감점으로 연결하지 않는다. CCSARP 직접성 체계는 연구자용 기술 코딩으로 검토하되, 현재의 target-feature별 band나 학습자 화면을 자동 대체하지 않는다.

## 7. R의 화행별 조작화

공통 `low | mid | high` 값은 유지하되, R은 보편적인 단일 부담이 아니라 화행별 `interactional weight`로 조작화한다.

| 화행 | R의 잠정적 의미 |
|---|---|
| 요청 | 상대가 부담할 시간·노력·위험 |
| 거절 | 거절이 상대 계획에 미치는 영향 |
| 사과 | 위반·피해의 심각도 |
| 감사 | 받은 호의의 크기 |
| 제안 | 제안된 행동의 비용·결과 |
| 초대 | 참여에 필요한 시간·비용·약속 |
| 반대 | 이견의 이해관계와 관계적 민감도 |
| 칭찬 | 칭찬 대상의 개인적 민감도와 상호작용 무게 |
| 불만 | 피해의 심각도와 상대의 책임 정도 |

위 표는 설계 출발점이다. 각 화행의 target feature를 확정할 때 해당 문헌과 실제 자료로 다시 검증한다.

## 8. 번역과 통역

번역과 통역은 별도 과업·분석층으로 다룬다.

- 번역: 서면 표현, 수정 가능성, 기록성
- 통역: 실시간 처리, 음성, 휴지·억양·Gambit

AI 피드백도 모드에 따라 분기한다.

음성 없이 전사문만 있는 경우:

- 의미·문법·표현 선택: 평가 가능
- 억양·휴지·상호작용 타이밍: 평가 불가

통역 연구에서는 원전사, 학습자 확정전사, 필요한 경우 동의에 따라 보존한 음성 원본을 구분한다.

## 9. AI 비평기와 인간 검수

각 장치의 역할을 구분한다.

```text
프롬프트 해시 = 재현성
AI 비평기 = 결함 선별
교수자 Gate = 교육 콘텐츠 승인
복수 인간 평가자 = 연구 타당화
```

AI 비평기는 연구 타당성을 보증하는 검증자가 아니다. 인간 판정과 대조해 정확도가 확인된 선별 도구다.

## 실행 우선순위

### 동결 전

1. `9화행 = 교육 과제 유형` construct map 작성
2. focal interactional target 기준으로 생성·감사 규칙 수정
3. 직접성·공손성·격식·부담·적절성 분리
4. 화행별 R 정의 작성
5. 243 구인셀과 54 전달셀을 별도 감사표로 검산
6. topic을 P·D·mode 호환 사건 시드로 제한
7. Standard Situation 기반 최소 `context_spec` 설계
8. 명제적 Supportive Move와 Gate 1의 충돌 해결
9. 기존 18셀 재검증

본배치 승인 프리셋은 495건이다. 수준별 번역 쿼터 `13 / 15 / 14`, 통역 비율 `0.3`으로 화행당 55건을 만들며, 243 구인셀은 셀당 최소 2건, 54 전달셀은 셀당 최소 4건을 확보한다. 400건 이상 실행은 이 조건을 충족하지 않으면 차단한다.

### 연구 파일럿 전

1. MPJ 문항별 답과 확신도 저장
2. 번역·통역 피드백 분기
3. 인간 평가자용 코딩 지침 작성
4. AI 비평기와 인간 판정 대조

### 동결 후 확장

- CCSARP 직접성 세부 코딩
- Head Act·Supportive Move 분석
- RFIE 표현 자원
- 통역 Gambit·음성 분석

## 해석상 주의

- House & Kádár의 분류를 유일한 화행 존재론으로 선언하지 않는다.
- AI 생성 시나리오 500건은 교육용 문항 은행이며, 그 자체가 한·중 문화 차이의 실증 자료는 아니다.
- P·D·R만으로 전체 맥락을 대표한다고 주장하지 않는다.
- 특정 중국어·한국어 표현의 존재 여부를 화용적 적절성의 자동 정답키로 사용하지 않는다.
- MPJ 판단, 최초 DCT 산출, AI 피드백 후 수정 수행을 서로 다른 측정값으로 해석한다.
