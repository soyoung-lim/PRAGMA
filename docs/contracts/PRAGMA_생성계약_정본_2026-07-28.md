> 적용 범위: 코어 생성, Full Mission 승격, 자동검사, 사람 검수, 저장, provenance, 학습자 수행 로그

## 1. 제품·연구 경계

PRAGMA는 교육 우선형 학습 플랫폼이며, 수업 과정에서 연구 가능한 자료를 남긴다. 생성·평가·저장 계약은 교육 경험을 검사 도구처럼 축소하기 위한 장치가 아니라 다음을 보장하기 위한 기술 계약이다.

- AI 생성물이 사람 검수 없이 학습자에게 공개되지 않는다.
- 상황 적절성, 의미 충실성, 문법·형식 문제를 서로 섞지 않는다.
- 생성물과 학습자 수행의 버전·출처·변경 이력을 식별할 수 있다.
- 현재 자료만으로 교육 효과나 실제 상호작용 능력을 인과적으로 주장하지 않는다.

허용되는 제품·논문 설명은 다음 범위다.

> 맥락화된 번역·통역 과제에서 학습자의 화용적 판단, 표현 선택과 수정 과정을 지원하고 기록한다.

세부 정체성은 `docs/research/PRAGMA_PRODUCT_RESEARCH_IDENTITY_2026-07-28.md`를 따른다.

## 2. 데이터 층위

```text
scenario_core_v2
  └─ 선택한 코어만 Full Mission으로 승격
       └─ mission_v3 (MPJ4 + DCT1)
            └─ 사람 검수 후 reviewed
                 └─ 학습자 수행과 feedback/revision 기록
```

### 2.1 코어

- JSON 스키마: `scenario_core_v2`
- DB 외곽 `content_format='scenario_core_v1'`은 기존 행·RPC 호환을 위해 유지되는 이름이다.
- 코어는 상황, 관계, 출발문, 선행 발화와 요약 메타를 가진다.
- 코어에는 MPJ 문항과 DCT 참고안이 없다.
- 495 본 배치는 코어만 생성한다. 495개를 Full Mission으로 일괄 승격하지 않는다.

### 2.2 Full Mission

- 신규 스키마: `mission_v3`
- 신규 provenance: `prompt_version='mission_v3_mpj4'`
- 코어를 선택해 개별 승격하며, 생성 직후 상태는 `generated`다.
- `mission_v1/v2`는 legacy MPJ5 열람·회귀 호환용으로 보존한다.
- 기존 v1/v2를 v3로 백필하거나 신규 v3와 같은 생성 계열로 취급하지 않는다.

### 2.3 수행 로그

- 학습자 수행은 기존 `learner_mission_logs` 계열을 사용한다.
- 최초 산출, 제공된 피드백, 수정 산출, 완료 상태와 미션 식별자를 연결한다.
- 로그가 존재한다는 이유만으로 연구 이용 동의가 성립하지 않는다.
- 새 로그 필드나 의미 변경은 DB 스키마와 연구 주장 범위를 먼저 보고한다.

## 3. 생성 조건과 표본 층위

### 3.1 연구 구인행렬

```text
speech_act 9 × P 3 × D 3 × R 3 = 243셀
```

- `P`: 상대적 권력
- `D`: 사회적 거리
- `R`: 해당 화행의 상황 부담

P·D·R은 상황 적절성 판단의 조건이다. 직접성과 공손성을 하나의 축으로 합치지 않는다.

### 3.2 전달 커버리지

```text
speech_act 9 × learner_level 3 × task_mode 2 = 54셀
```

- `learner_level`: 입문·중급·고급의 교육 지원 수준
- `task_mode`: `translation | stt_interpreting`

54셀은 교육용 전달 커버리지이며 243셀과 같은 연구 구인행렬이 아니다. PRAGMA 수준을 CEFR·ACTFL 등급에 직접 대응시키지 않는다.

### 3.3 편성·사건 메타

- `domain`: 일상·학업·직장
- `theme`: 강좌 편성 영역
- `topic`: 구체적 사건 시드
- `industry`: 직장 장면의 분야 메타
- `context_spec`: P·D·R과 사건 시드의 내부 호환성 해결층

이 값들은 필요하지만 P·D·R과 같은 독립 화용 구인으로 과장하지 않는다.

## 4. 화행과 target feature

교육용 화행은 9종이다.

- 요청
- 거절
- 감사
- 사과
- 제안
- 초대
- 반대
- 칭찬
- 직접 불만

9화행 모두 사람이 작성한 기본 `target_feature`를 가진다. 칭찬하기와 칭찬 대응은 교육적으로 구분된 feature로 보존하되, 현재 `compliment` 코어의 자동 승격 기본값은 칭찬하기 feature다.

계약 원칙:

- `targetFeatures.ts`의 코드·version·band schema가 실행 정본이다.
- AI가 target feature, band code, learner label을 임의로 만들지 않는다.
- 모든 band는 인간 캘리브레이션 전 `proposed` 지위다.
- 표현 자원은 가능한 실현 수단이지 고정 정답 목록이 아니다.
- 한 화행에 복수의 기능적 head와 supportive move가 함께 나타날 수 있다.
- 상황 적절성, 직접성·공손성, 화행별 target feature를 분리해 해석한다.

### 4.1 `usable_facts` 폐쇄 목록

명제적 supportive move는 코어의 `usable_facts` 또는 출발문에 있는 사실만 사용할 수 있다.

- 최대 8개
- 목록 밖의 이유, 대안, 수리, 보상, 재발 방지 약속, 새 일정 추가 금지
- 사실의 유무를 MPJ 정답 단서로 사용 금지
- 관습화된 사과·인사, 완화어, 호칭 같은 비명제적 자원은 폐쇄 목록 대상이 아니다.

## 5. 코어 생성 계약

### 5.1 모델과 응답 형식

- 모델: `gpt-4.1-mini`
- 일반 폴백: `gpt-4o-mini`
- API: Chat Completions
- 코어 출력: strict Structured Outputs
- `strict: true`
- `additionalProperties: false`

필수 모델 출력 5필드:

```text
situation_ko
relation_ko
source_text
preceding_turn
brief_note_ko
```

출력 키와 DB 저장 구조는 strict 적용 전과 같다. strict schema 적용은 출력 형식 강화이며, 내용 타당성을 자동 보장하지 않는다.

### 5.2 코어 생성 계열

현재 코어 표면 해시:

```text
4c996a00259cf54dcc23b03d0998f7afd3926a95c284ed23719910ebb1d871c0
```

해시에는 다음이 포함된다.

- system/user 프롬프트 템플릿
- 서버 주입 카탈로그와 조립 규칙
- 모델과 폴백 모델
- temperature
- response format
- strict JSON Schema 전문

셀별 화행·수준·도메인·P/D/R 값은 각 행의 구조화 필드로 저장하며 표면 해시에 넣지 않는다.

해시가 바뀌면 이전 계열 생성물과 같은 동결 집합으로 섞지 않는다.

### 5.3 코어 자동검사

- 결정론 검사: 스키마·축·모드·인접쌍·topic·산업 등 저장 전 규칙
- 보조 AI 비평: `core_quality_v4`, 12축
- 사람 눈검사: 최종 콘텐츠 판단

AI 비평의 `pass`는 사람 검수나 내용 타당화를 대체하지 않는다.

## 6. Full Mission 생성 계약

### 6.1 현행 구현 기준선

신규 `mission_v3`의 순서는 다음과 같다.

```text
scale4
→ judge3
→ fix_choice
→ reason_conf
→ DCT 번역 또는 통역 산출
→ 피드백
→ 수정
```

- `multi_judge`는 신규 Full Mission에서 제외된다.
- legacy `mission_v1/v2` MPJ5는 계속 읽고 검사할 수 있다.
- `reason_conf`에만 이유 선택과 확신도가 있다.
- DCT는 MPJ와 같은 `mission_id`, attempt와 `target_feature`에 속한다.
- MPJ 완료만으로 미션 완료 처리하지 않는다.

### 6.2 보류 중인 제품 결정

MPJ4는 2026-07-28 현재 구현 기준선이지 차기 구조의 최종 승인 선언이 아니다. 다음 대안은 논의만 되었고 승인되지 않았다.

```text
Scale4
→ Judge3 + FixChoice
→ Judge3 + Reason/Confidence
→ MultiJudge 5후보
→ DCT
```

사용자 승인 전 다음을 하지 않는다.

- `mission_v4` 구현
- MPJ 순서·유형 변경
- 새 프롬프트·DB migration·Edge 배포
- 기존 v3 생성물과 새 구조 혼합

### 6.3 미션 모델과 형식

- 미션 승격 모델: `gpt-4o`
- 현재 미션 출력: JSON mode
- 미션 strict JSON Schema: 미구현
- 생성 후 결정론 검사
- 실패 시 전체 미션 재생성, 최대 2회
- 필드 단위 repair와 outline 파이프라인은 사용하지 않는다.

## 7. 평가와 피드백 경계

### 7.1 분리 원칙

피드백은 최소 다음 층을 구분한다.

1. 의미·의도 충실성
2. 명백한 문법·형식 문제
3. 해당 target feature의 상황 적절성

직접성, 공손성, 의미 충실성을 하나의 총점으로 합치지 않는다. 더 길거나 더 완곡한 표현을 자동으로 더 좋은 답으로 판정하지 않는다.

### 7.2 사람 검수

상태 흐름:

```text
core-only
→ generated
→ AI/결정론 검사
→ 사람 검수
→ reviewed
```

- 일반 학습자 공개 최소 조건: `mission_status='reviewed'`
- 연구 분반에서 band를 측정 주장에 사용할 경우: `reviewed`와 별도의 인간 캘리브레이션 상태가 필요하다.
- `generated`는 생성 성공이지 교육적 승인 상태가 아니다.

## 8. provenance와 재현성

코어와 미션은 최소 다음을 식별할 수 있어야 한다.

- model
- provider
- prompt version
- prompt snapshot hash 또는 mission content hash
- generated_at
- generation attempt
- schema version
- language direction

Edge가 계산한 `prompt_snapshot_hash`를 클라이언트가 변형하거나 로컬 코드로 재계산하지 않는다. 프롬프트 정본 화면은 배포 Edge 소스에서 생성된 저장소 스냅샷과 저장 행의 지문을 대조한다.
